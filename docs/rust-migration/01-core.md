# core module → `crates/ss-core` (lib crate)

Java module `io.bitken.ss.core`: 4 packages + one generated package + one
templated class. Everything below becomes one Rust lib crate with four modules.
Conversion order: plan (warm-up) → model (risk spike) → gw → conf — see
00-overview.md §Starting sequence for the rationale; sections below stay in
model-first order because model is the load-bearing design, not because it
converts first.

## 1. `io.bitken.ss.jaxb` (xjc-generated from plan-tasks.xsd) → `ss_core::model`

The only *generated* code in the project. Do **not** transliterate the generated
classes — regenerate the model by hand from `plan-tasks.xsd` (≈130 lines, easy
for the LLM to read directly) as plain serde structs over `quick-xml`:

```rust
#[derive(Serialize, Deserialize)]
#[serde(rename = "plan-tasks")]
pub struct PlanTasks {
    pub plan: u32,
    #[serde(rename = "plan-version")]
    pub plan_version: String,          // pattern plan-[0-9]+-v[0-9]+ enforced on write
    pub metadata: Metadata,
    pub tasks: Tasks,
    #[serde(rename = "project-updates")]
    pub project_updates: ProjectUpdates,
}
```

- Enums `PlanStatusType` (`active|complete|abandoned|in-review`),
  `TaskStatusType`, `RiskLevelType` (note: risk allows `""`), `DeviationTypeEnum`
  → Rust enums with `#[serde(rename = "...")]`; keep `fromValue`-style parse
  errors identical in message shape where tests assert on them.
- `BigInteger` ids → `u32` (ids are small positive ints; nothing needs bignum).
- `XMLGregorianCalendar` → newtypes `XmlDate(time::Date)` /
  `XmlDateTime(time::OffsetDateTime)` with XSD lexical (de)serialization.
- **`xs:any` extension points** on `TaskType` and `MetadataType`: this is where
  `<depends-on>` lives (see TaskStore.getDependsOn/setDependsOn, which walk DOM
  `Element`s). Model as `extensions: Vec<RawElement>` where `RawElement`
  preserves name + raw inner XML untouched, so unknown future fields survive a
  read-modify-write cycle.
- **SETTLED (plan-102 spike):** the model is implemented on the quick-xml
  **event API** end-to-end — generic tree parse (`raw.rs`) → typed mapping,
  plus a hand-rolled `layout.rs` writer reproducing JAXB's formatted output
  byte-for-byte. Values are stored as **lexical strings** (leniency parity
  with JAXB) with typed accessors (`enums.rs`) validating on demand. serde
  derive is ruled out: no ordered `xs:any` capture, no `<x></x>` vs `<x/>`
  distinction, and the JAXB layout needs a custom writer regardless. The
  golden corpus (`exp/rust/fixtures/`) round-trips byte-identically; the
  hand-edited unknown-extension fixture normalizes idempotently, matching
  JAXB's own re-indent (fixtures 06 → 07).
- Writer must reproduce JAXB formatted output closely (XML decl, indentation)
  to avoid mass-reformatting existing user files — golden round-trip test:
  read a Java-written fixture, write it back, diff must be empty (or a single
  agreed normalization).
- XSD validation: JAXB never validated on read (no schema set), so the Rust
  reader is lenient too; enums may need an `Unknown(String)` escape hatch if
  fixture files show tolerance is actually exercised.

Tests: round-trip fixtures generated by the *Java* CLI (check several real
plan-N-tasks.xml files in as test resources before starting).

## 2. `io.bitken.ss.svc.plan` → `ss_core::plan`

Ten classes, almost all pure logic — the easiest package, and the warm-up
slice converted *first* to establish crate-wide conventions (error style, test
layout, verbatim format strings) cheaply. Note: `PlanSummaryFormatter` takes
`&PlanTasks`, so its signature lands with a placeholder until the model exists
— convert its pure formatting logic against a minimal stub struct, then swap
in the real model type in step 2.

| Java | Rust | Notes |
|---|---|---|
| `Slugs` (static util) | free fn `slugify(&str) -> String` | Port `SlugsTest` verbatim |
| `PlanNumbers` | struct holding `plans_dir: PathBuf` + regex | Scans dir for `plan-(\d+)` files; next-number logic |
| `PlanMarkdownParser` | struct or free fn, `regex` crate | The `### Task N: name [Risk]` heading pattern; `Pattern.MULTILINE\|CASE_INSENSITIVE` → `(?im)` |
| `PlanMarkdown` | struct over locator | `sliceTaskSection` markdown slicing |
| `PlanSummaryFormatter` | fn `format(&PlanTasks) -> String` | Output string is asserted by tests — copy format strings exactly |
| `Stub` | `const` template + fn | Plan markdown stub text |
| `NewPlan` | struct (plan_numbers, git_state, locator) | Scaffolding: next number, slug, write stub, branch |
| `PlanService` | struct (task_store, new_plan) | Thin façade; keep it or inline — keep, cli leaves call it |
| `ScaffoldResult` / `ScaffoldException` | struct + `thiserror` variant | — |

Error model for the whole crate: one `ss_core::Error` enum via `thiserror`
(variants: Xml, Io, Scaffold, StateRootUnsettled, InaccessibleRoot, TaskNotFound
…). Java's checked `JAXBException`/`Exception` signatures all become
`Result<_, Error>`.

## 3. `io.bitken.ss.gw` → `ss_core::gw`

Three classes.

- **`GitState`**, **`GitTags`** — mechanical: every method is a
  `std::process::Command::new("git").args(...).current_dir(&self.work_dir)`
  call. Preserve the exact semantics:
  - `runLines` swallows spawn errors → empty vec (methods like `isClean` treat
    "git unavailable" as clean/empty — keep that, tests depend on graceful
    degradation).
  - `runExitCode` merges stderr into stdout and prints failures to stderr.
  - GitTags derives the highest `plan-{N}-v*` tag, falling back to `-v1`.
  - Always run in the configured workdir, never inherited CWD (the plan-70
    lesson lives in the GitTags class comment — keep it).
- **`TaskStore`** — the largest class (299 lines) but mostly a typed façade
  over the model:
  - `read_plan_tasks`: keep the 5×100 ms retry loop verbatim — it papers over
    the reader/renamer race documented in the comment.
  - `write_plan_tasks`: write `<path>.tmp`, `fs::rename` over the target
    (atomic), clean up tmp on failure — direct translation.
  - `generate/add/find/update/comment/deviation/set_commit/project_update`:
    plain struct manipulation once the model is native Rust (no ObjectFactory,
    no BigInteger, no DatatypeFactory — this class shrinks by half).
  - `getDependsOn`/`setDependsOn`: reads/writes the `<depends-on>` extension
    element via the `RawElement` list from §1 instead of DOM.
  - The deprecated `parseTasksFromPlan` pass-through: drop it; callers use the
    parser directly (verify no cli caller first).

- **PORTED (plan-107, 2026-08-19).** All three classes plus
  `PlanMarkdown.sliceTaskSection` are ported and verified against XML the real
  Java binary wrote. `parseTasksFromPlan` was dropped as planned (no cli
  caller). Coverage 99.35–99.75% region, 98–100% line per file.
  - **Timestamps are their own module** (`gw::xml_time`), not inline helpers:
    reproducing `XMLGregorianCalendar`'s lexical output needed a hand-rolled
    writer, because no `time` format description produces Java's
    `Z`-for-zero-offset rule. The contract — always three fractional digits,
    `Z` never `+00:00`, sub-millisecond floor-truncated, minute-granular
    offset — is pinned against the fixture corpus.
  - **Two injectable seams** carry the parts that would otherwise be
    untestable: `TaskStore`'s clock (`Clock = Box<dyn Fn() -> OffsetDateTime>`,
    default `system_now`) and `GitState`'s diagnostics sink
    (`Diagnostics = Box<dyn Fn(&str)>`, default `eprintln!`). The second is not
    in the Java shape at all; it exists because plan-107 makes git's exact
    stderr strings contract and `eprintln!` cannot be asserted on in a Rust
    unit test.
  - **`PlanMarkdown` split by layer**: the slicing is a pure function in
    `plan::markdown` taking the markdown text, and `TaskStore` owns the file
    read. Java's class did both. Behaviour is identical — a missing or
    unreadable plan file still slices to `""`.
  - **Divergences from Java, all deliberate and commented at the call site:**
    - `GitTags::version_number` returns `None` for a tag like `plan-7-v1-rc`
      and derives `v1`; Java parses the suffix after the last `-v` and throws
      `NumberFormatException`. Degrading fits GitTags' everything-degrades
      contract.
    - `run_exit_code` concatenates stdout and stderr, where Java's
      `redirectErrorStream(true)` interleaves them live, so ordering can differ
      for a command writing to both. Nothing in the corpus depends on it.
    - `get_depends_on` and `add_comment` return `Result` because Java's
      `findTask` throws for an unknown id; `get_task_name` stays total because
      Java's resolves through a stream default to the stringified id.
  - **Fidelity finding worth keeping:** `is_branch_pushed_and_not_ahead` is the
    one *read* query that emits a diagnostic, because Java probes for the
    upstream with `runExitCode` rather than `runLines`. Every other read query
    degrades silently.

## 4. `io.bitken.ss.conf` → `ss_core::conf`

Ten files, but half are Dagger/JPMS scaffolding that does not port:

**Ports directly:**
- `ShipsmoothDataLocator` — pure path arithmetic (`.shipsmooth/plans/…` layout
  under repo root vs state root). Core of the crate; port with its validation
  tests.
- `ResolvedStateRoot` — validating newtype; `of(path)` checks accessibility and
  is the *only* constructor (keep the private-ctor invariant via a private
  field + `pub fn of`).
- `ExperimentalMode` — bool newtype + `FLAG` const (`--enable-experimental`).
- Exceptions (`StateRootUnsettledException`, `InaccessibleRootException`) →
  `Error` variants with identical message text (the cli gate and skill match
  on behaviour driven by these).

**Does not port (replaced, not translated):**
- `ServicesModule` / `AppComponents` / `DaggerAppComponents` / `@RepoRoot` /
  `@StateRoot` qualifiers / `jakarta.inject.Provider` — the whole DI layer.
  Replacement: a plain `Services` struct in ss-core with two constructors:

  ```rust
  pub struct Services { pub locator: ShipsmoothDataLocator, pub task_store: TaskStore, ... }
  impl Services {
      pub fn settled(repo_root: PathBuf, state_root: PathBuf, exp: ExperimentalMode) -> Result<Self> { ... }
      // unsettled mode needs no struct at all — see 02-cli.md §wiring:
      // clap parses before services exist, so state-independent commands
      // simply never construct Services.
  }
  ```

  The Provider laziness existed solely so picocli could *instantiate* command
  objects (to render --help) before the state root settles. clap commands are
  data, not objects; parse → match → *then* build `Services` only for
  state-dependent commands. `StateRootUnsettledException` becomes a normal
  `Err(Error::StateRootUnsettled)` returned from `Services::settled` /
  emitted by the dispatch layer when resolution is not `Settled`.
- `FeatureFlags` interface → a `fn experimental(&self) -> bool` on the command
  enum, or a match arm list in the tree builder.

## 5. `java-templates/Build.java` → `build.rs`

`VERSION` and `EXPERIMENTAL_BUILD` are baked at compile time today (with the
plan-75 staleness guard). Rust equivalent:

- `VERSION`: `env!("CARGO_PKG_VERSION")`, with workspace version as the single
  source (replaces `plugin.version` in gradle.properties — decide which file
  is canonical during the release-pipeline follow-up).
- `EXPERIMENTAL_BUILD`: a cargo feature `experimental` (`cfg!(feature =
  "experimental")`). Features are part of the build fingerprint, so the
  "stale Build.java ships wrong flag" defect class (plan-75 Defect 1) is
  structurally impossible — no input-declaration ceremony needed.

## module-info.java, shadow, xjc, jlink shading

All deleted with no replacement. `reinjectModuleInfo`, the Semeru jar-tool
dance, the shaded `core-jlink.jar` classifier, and the JPMS `opens` clauses
exist only because of Java's module/runtime-image system.
