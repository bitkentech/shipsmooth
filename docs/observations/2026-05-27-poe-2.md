# Domain Model approach for `plugin-tasks-java`

## Where the code sits today

Mapping current structure to PoEAA patterns:

| Today | PoEAA pattern |
|---|---|
| `XmlService` (CRUD over JAXB graph, anaemic `PlanTasks`/`TaskType`) | **Table Data Gateway** mislabelled as a service |
| `LedgerService` + `ObjectStore` | **Gateway** to the append-only ledger file (fine as-is) |
| JAXB-generated `PlanTasks`, `TaskType`, `CommentType`, `DeviationType` | Anaemic data holders — no behaviour |
| `commands/*Command` (UpdateStatus, AddComment, Claim, ...) | **Transaction Script** — each command reads XML, mutates, writes, records ledger event |
| `WorkflowServiceImpl` (596 lines orchestrating worktree → ledger → XML → resolver) | A 4-script god-class — Transaction Scripts wearing a Service Layer hat |
| `IntegrationLedger` | Small **Mapper** over the ledger for plan-scoped events |

Symptoms of the Transaction-Script-without-Domain-Model split: command code knows how to find a task in a list, how to construct `CommentType`, when to record which event, and `WorkflowServiceImpl` knows worktree paths, branch names, SHA invariants, *and* JAXB structure all in one place.

## What the domain model looks like

Three aggregate roots emerge from the language already in the code:

### 1. `Plan` aggregate (root: `Plan`)
Wraps `PlanTasks`. Replaces most `XmlService` mutator methods.

```
Plan
 ├── id, version, status, metadata
 ├── tasks: List<Task>          (Task is the entity inside the aggregate)
 ├── projectUpdates: List<Update>
 ├── task(int id): Task
 ├── recordProjectUpdate(status, blocked, message)
 └── close(version)
```

`Task` (entity, identity = `id` within plan):
```
Task
 ├── id, name, risk, status, commit, createdFrom, closedAtVersion
 ├── dependsOn: List<TaskId>    (Value Object list, parsed once)
 ├── comments, deviations
 ├── updateStatus(TaskStatus)   ← was XmlService.updateTaskStatus
 ├── addComment(message)        ← was XmlService.addComment
 ├── addDeviation(type, msg)
 ├── setCommit(sha)             ← only via WorkRecord, see below
 └── isReadyToIntegrate(): bool
```

Value Objects: `TaskId`, `PlanId`, `CommitSha`, `BranchName` (`agent-work/{id}`, `integration/plan-{n}`), `WorktreeRel` (`.agents/tasks/{id}` / `.agents/integration/plan-{n}`), `TaskStatus`, `DeviationKind`, `DependsOn`. These are the strings being concatenated and parsed in `WorkflowServiceImpl` lines 65-66, 95-96, 223-225, etc.

### 2. `Ledger` aggregate (root: `Ledger`)
Already close — `LedgerService` becomes the Repository/Gateway, `Event` stays a Value Object, but query semantics move into the domain:

```
Ledger
 ├── append(Event): EventHash
 ├── eventsFor(TaskId): EventStream
 ├── lastEvent(TaskId, EventType): Optional<Event>
 └── timeline(): List<Event>

PlanLedgerView (replaces IntegrationLedger)
 ├── recordIntegrationPlan(order, branch)
 ├── recordPatchIntegrated(taskId, sha, agentWorkSha)
 ├── recordIntegrationComplete(...)
 └── alreadyIntegrated(order): Set<TaskId>   ← was resumeAlreadyIntegrated
```

### 3. `Integration` aggregate (root: `Integration`)
This is the big extraction from `WorkflowServiceImpl`. The state-machine of "merge order, attempt, conflict, resolver, retry budget, complete" lives here, not in 400 lines of private methods.

```
Integration
 ├── plan, taskBranch, integrationBranch, worktree
 ├── pendingMerges: List<TaskMerge>
 ├── alreadyIntegrated, failures
 ├── plan(): MergeOrder
 ├── attempt(TaskMerge): MergeOutcome   (clean | conflict | verifyFailed)
 ├── resolve(MergeAttempt, Resolver): MergeOutcome
 └── finalize(): IntegrationResult

TaskMerge (value)
 ├── taskId, agentBranch, agentWorkSha, filesTouched
MergeAttempt (value — already exists as a private record!)
MergeOutcome (sealed: Integrated | Conflict | VerifyFailed | Abandoned)
```

The `IntegrationContext`, `TaskMerges`, `WorktreePrep`, `MergeAttempt`, `OneShotResult` records currently nested in `WorkflowServiceImpl` are evidence that this aggregate already exists in spirit — it just hasn't been named or moved out.

## Layering after the refactor

```
commands/        ← thin CLI adapters: parse args, call Service Layer, render
  UpdateStatusCommand → planRepository.find(plan).task(id).updateStatus(s)
                        planRepository.save(plan)
                        ledger.append(Event.statusUpdated(...))

application/     ← Service Layer (NEW — explicit, thin)
  WorkflowService           (initializeWorker, finalizeWorker, runIntegration)
  IntegrationCoordinator    (orchestrates Integration aggregate + git + resolver)

domain/          ← Domain Model (NEW)
  plan/        Plan, Task, TaskStatus, TaskId, DependsOn, CommitSha, ...
  ledger/      Event, EventType, EventHash, Ledger, PlanLedgerView
  integration/ Integration, TaskMerge, MergeAttempt, MergeOutcome, MergeOrder
  git/         BranchName, WorktreeRel, Sha (value objects)

infrastructure/  ← Data Mapper + Gateway
  XmlPlanRepository  (replaces XmlService — Data Mapper between Plan and JAXB graph)
  FileLedger         (was LedgerService, now implements ledger.Ledger port)
  GitWorktreeGateway (was WorktreeService)
  ProcessRunner, SubagentRunner
```

## High-level class-structure changes

| Change | From → To |
|---|---|
| Add **`Plan`/`Task`** domain entities; behaviour moves off `XmlService` | `XmlService.updateTaskStatus(planTasks, id, s)` → `task.updateStatus(s)` |
| Rename + repurpose `XmlService` as **Data Mapper** | `XmlService` → `XmlPlanRepository implements PlanRepository` with `find(PlanId): Plan` and `save(Plan)` |
| Introduce **Value Objects** for the string-typed primitives | replace `String taskId`, `String branch`, `String worktreeRel` across the codebase with `TaskId`, `BranchName`, `WorktreeRel` |
| Extract **`Integration` aggregate** from `WorkflowServiceImpl` | the 4 nested records + 10 private methods move into a real class with state and lifecycle |
| Slim `WorkflowServiceImpl` to a **Service Layer** | becomes a ~100-line coordinator that wires repository → aggregate → gateway → ledger |
| Rename `IntegrationLedger` → **`PlanLedgerView`** as a Repository projection | also absorbs `resumeAlreadyIntegrated` from `WorkflowServiceImpl` |
| `commands/*` become **Transaction Scripts at the boundary only** | each command shrinks to ~15 lines: parse, load aggregate, invoke method, save, record event |
| Introduce a **`Transaction`/Unit-of-Work** wrapper around `Plan` + `Ledger` writes | the existing `Transaction` class generalises — every command that mutates XML *and* appends ledger needs this; current code does it ad-hoc |
| `Event` factory methods grow **named constructors per kind** | `Event.statusUpdated(taskId, status)`, `Event.patchEmitted(...)`, `Event.commitRecorded(...)` — moves the metadata-key strings out of caller code |

## Expected payoff

- `WorkflowServiceImpl` drops from ~600 to ~120 lines; the integration state machine is independently unit-testable without git or ledger fakes.
- Commands stop knowing the JAXB shape — they call `plan.task(id).addComment(...)`. Adding a new field to `TaskType` no longer ripples through 8 commands.
- The `String taskId` / `String branch` / `String sha` confusion (already a footgun — see `branchSha` vs `headSha` vs `agentWorkSha` in `WorkflowServiceImpl`) becomes a type error.
- The `IntegrationContext`/`TaskMerges`/`WorktreePrep` records currently hidden as inner classes graduate into named domain concepts that documentation and ADRs can refer to.

## Where to NOT push the model

- `LedgerService` is genuinely a Gateway over an append-only file; don't promote `Event` to an entity with mutators — keep it a Value Object.
- `git/` services are correctly Gateways to an external system. Don't try to model "branches" as domain entities — they're identifiers, value objects at most.
- `commands/` should stay Transaction Scripts. The mistake is *putting domain logic in them*, not the script shape itself.
