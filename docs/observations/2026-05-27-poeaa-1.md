# PoEAA Code Review — `plugin-tasks-java/src/main/java`

Date: 2026-05-27

## Overall pattern map

The codebase is well-aligned with several PoEAA patterns, especially in the boundaries. The shape is essentially:

```
PicoCLI commands  →  WorkflowService  →  domain services (git, ledger, xml)
   (Front layer)    (Service Layer)        (Gateways / Mappers / Repos)
```

| Layer | Pattern in use | Verdict |
|---|---|---|
| `commands/*` | **Page Controller** (one class per CLI command) | Fits. Idiomatic for PicoCLI. |
| `WorkflowService` / `Impl` | **Service Layer** (operation script flavor) | Strong fit. Thin interface, transactional unit boundary. |
| `WorktreeService` | **Gateway** | Strong fit. |
| `LedgerService` + `ObjectStore` | **Gateway** + content-addressed store | Strong fit; effectively an event-store gateway. |
| `IntegrationLedger` | **Mapper** (between domain ops and ledger events) | Strong fit. |
| `XmlService` | **Table Data Gateway** with mapper leakage | Mixed — see below. |
| `Transaction` | **Unit of Work** (narrow, hand-rolled) | Reasonable; named honestly. |
| `ServicesModule` | **Registry** via Dagger | Fits. |
| `IntegrationOptions` | **Data Transfer Object** | Fits — parameter object. |
| `IntegrationContext` / `TaskMerges` / `MergeAttempt` (records) | **Parameter Objects** | Good. |

The domain logic style is **Transaction Script**, not Domain Model — and that is the right choice here. Tasks/plans/events are mostly data; behavior lives in services. Don't be tempted to convert these to a Domain Model; the gain would not justify the cost.

---

## Strengths worth keeping

1. **Service Layer boundary is clean.** `WorkflowService` (workflow/WorkflowService.java:13) exposes only three operations: `initializeWorker`, `finalizeWorker`, `runIntegration`. Commands route through it instead of touching git/ledger/xml directly. This is the textbook Service Layer — a thin facade with a defined API surface.

2. **Gateways are properly encapsulated.** `WorktreeService` (git/WorktreeService.java:20) is a Gateway over the `git` CLI. All process spawning goes through one injected `ProcessRunner`. Callers never construct `ProcessBuilder` themselves. This is the Gateway pattern done right.

3. **Content-addressed ObjectStore is a good Gateway.** `ObjectStore.writeObject` (ledger/ObjectStore.java:21) gives you a write-once, dedup-by-hash store. The atomic temp-file + rename + idempotent-on-exists pattern (lines 36-48) is excellent — concurrent writers cannot corrupt each other.

4. **`Transaction` is named honestly.** Its Javadoc explicitly says *"not a generic transaction framework"* (workflow/Transaction.java:10-13). It's a narrow Unit of Work — register inverse, commit, rollback. Many codebases over-build this; you didn't.

5. **`IntegrationLedger` is a clean Mapper.** Wraps `LedgerService` and converts integration domain events to ledger writes (integration/IntegrationLedger.java). Hides metadata-key conventions from callers.

6. **Parameter objects via records** in `WorkflowServiceImpl` (IntegrationContext, TaskMerges, MergeAttempt — lines 562-595). Without these the helper methods would have 8–10 parameters each.

## Findings

### 1. `XmlService` mixes Table Data Gateway with Domain-Object methods — Repository would fit better

**Location:** `service/XmlService.java`

The class blends three responsibilities:
- **Gateway** over the XML file (`readPlanTasks`, `writePlanTasks`, `planTasksFile`, atomic-rename logic).
- **Mapper** for the JAXB `PlanTasks` tree (`getTaskName`, `getDependsOn`, `setDependsOn`, `findTask`).
- **Domain mutators** (`updateTaskStatus`, `addComment`, `addDeviation`, `setCommit`, `projectUpdate`).

Symptom: callers always do `readPlanTasks → mutate → writePlanTasks` (see `WorkflowServiceImpl.finalizeWorker` lines 131-154 and `backfillTaskCommitShas` lines 435-457). The mutation methods take the in-memory tree and rely on the caller to remember to write it back. That's a classic missing-Repository smell — the persistence boundary is not where the file says it is.

**Suggested PoEAA shape:**
- **`PlanTasksRepository`** — owns file I/O (`load(planId)`, `save(plan)`), the retry-on-read race, and atomic write. Hide JAXB.
- **`PlanTasks` mutators as Domain Model methods** *or* as a `PlanTasksOperations` (stateless functions on the in-memory tree). The current naming (`updateTaskStatus`, `addComment`) already reads like a Domain Model — the data just isn't carrying the behavior.

This is the highest-leverage refactor in the package. Not urgent; the current shape works.

### 2. `LedgerService.findLast*` smells like a Query Object opportunity

**Location:** `ledger/LedgerService.java:87`, `:103`, `:125`

Three near-identical full-scans:
- `findLastEvent(taskId, type)` — filter by task + type
- `findLastEventIndex(type, metadataMatch)` — filter by type + metadata
- `findLastEventAfter(taskId, type, afterIndex)` — filter by task + type + index range

Each iterates `readHashes()` then deserializes every event. With N events this is O(N) per query, and there are many queries per `runIntegration` call (one `findLastEvent` per task plus one `findLastEventAfter` per task — see `WorkflowServiceImpl` lines 241, 314).

**Suggested fix:** a small **Query Object** that builds the predicate (`type`, `taskId`, `afterIndex`, `metadataFilter`) and executes once over a cached scan. Or — simpler — pull `readHashes()` and the deserialized list into a per-`runIntegration` cache (the integration loop only reads, never appends, until it records its own events). A request-scoped **Identity Map** of `sha → Event` would prevent the same blob from being deserialized 3-4 times during one integration.

This is a real perf hazard the moment ledgers grow past a few hundred entries.

### 3. `XmlService.parseDependsOn` prints to stderr; no Special Case

**Location:** `service/XmlService.java:61-72`

```java
System.err.println("parseDependsOn: skipping malformed entry '...'");
```

Two issues:
- Library code printing to stderr is hard to test and out of band for the rest of the pipeline which goes through `ProgressReporter`.
- Malformed input is silently dropped. If `depends-on="abc"` is meaningful, the caller should learn about it.

Either bubble it up (throw or return a `ParseResult` Special Case) or route through the same reporter the workflow uses.

### 4. `WorkflowServiceImpl.runIntegration` is approaching Service-Layer ceiling

596 lines, one class, with internal records doubling as a parameter passing protocol between the eight private helpers. It's still readable — the helpers are short and the records are well-named — but you are one feature away from this being uncomfortable.

**PoEAA suggestion:** extract an **`IntegrationCoordinator`** (or `IntegrationOperation` Transaction Script) that holds the `IntegrationContext` + collaborators as fields, so the private methods become instance methods on a per-run object instead of passing `ctx` through every signature. The `WorkflowService` interface stays as the boundary; the coordinator is an internal collaborator. This is exactly the pattern from Fowler's chapter on Service Layer (operation script): the Service Layer stays thin and delegates the multi-step orchestration to a per-call object.

Don't do this yet — wait for the next integration feature to force the issue. But know the lever is there.

### 5. `verifyLedger` writes to `System.err` from inside `LedgerService`

**Location:** `ledger/LedgerService.java:140-152`

Same concern as #3. A Gateway method that side-effects to `stderr` couples persistence to presentation. The `verify` CLI command (LedgerCommand.java:118-127) should iterate and print; `LedgerService.verifyLedger` should just return the timeline.

### 6. Two layout helpers fight for ownership of `.agents/plans/...`

**Location:** `AgentsLayout.java` and `XmlService.planTasksFile` / `planMarkdownFile` (service/XmlService.java:33-40).

Path conventions live in two places. If `AgentsLayout` is the canonical Registry of project paths, the `planTasksFile` and `planMarkdownFile` on `XmlService` should delegate to it. Otherwise rename `AgentsLayout` or fold it in.

### 7. `ProcessRunner` is a Gateway — the verify-cmd path leaks string-shell

**Location:** `processes.runVerify(ctx.integrationDir, ctx.verifyCmd)` in WorkflowServiceImpl.java:379, :511

The `verifyCmd` is a free-form string from CLI options. If it's split on whitespace inside `DefaultProcessRunner`, multi-word arguments and quoted paths will fail. If it's passed to a shell, command injection is on the table. Worth verifying. The PoEAA framing: a Gateway should sanitize/validate inputs at the boundary, not pass-through.

### 8. `Event.forTask` / `Event.system` static factories — borderline Value Object, but mutable metadata?

**Location:** ledger/Event.java (inferred from `Map.of(...)` usage at WorkflowServiceImpl.java:79, :149, :151).

If `Event` is a record with a `Map<String,String> metadata` field, and callers pass `Map.of(...)` immutable maps, that's fine — Value Object semantics. If `Event` exposes a mutable `Map`, callers can mutate persisted history. Confirm the record's map is wrapped or immutable.

## Items NOT worth changing

- **Page Controller per command** is right for PicoCLI; don't reach for Front Controller.
- **Transaction Script over Domain Model** — your domain is workflow-coordination, not business rules. Don't model "Plan" and "Task" as behavior-rich objects; the ROI is negative here.
- **Hand-rolled `Transaction`** — keep it. A real Unit of Work framework is overkill.
- **Dagger as Registry** — appropriate at this size.
